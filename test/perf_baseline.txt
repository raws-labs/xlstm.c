# xlstm.c performance baseline - callgrind. Two numbers per row:
# Ir, retired instructions, and D1, simulated first-level data misses.
#
# Regenerate deliberately with:  make perf-baseline
# Checked by:                    make perf   (tolerance +2.0% / -5.0%)
#
# Two rows per case, one per XLSTM_GATES build (see include/xlstm_util.h).
# Every pair should differ: the switch reaches the f32 kernels too.
#
# Counts are the inclusive cost of one kernel entry point over 200 steps,
# collection toggled on that symbol alone. Exact and reproducible for a given
# binary, so any movement here is a real change in work done, not noise.
# That cuts both ways: make perf fails on a large improvement too, because an
# unrecorded win leaves a baseline generous enough to hide a later regression.
#
# These numbers describe the HOST backends only. They say nothing about cortexm
# or esp, whose performance is a property of those cores and is measured on
# hardware.
#
# D1 is the locality half, over a cache pinned in the Makefile rather than
# detected: --I1=32768,8,64 --D1=32768,8,64 --LL=8388608,16,64.
# It is a fixed yardstick for comparing two versions of this code, NOT a model
# of any target - the Cortex-M parts have no data cache or a much smaller one.
# It is also more fragile than Ir. The kernel copies argv and envp onto the
# initial stack, so the environment shifts every buffer against a cache line:
# one unchanged binary measured 7654, 7853 and 6457 under three environments
# differing only in padding. That is why perf-measure runs under env -i.
# Rows whose D1 baseline is under 50 are reported and not gated: that
# working set fits the cache, so what is left is compulsory misses.
#
# Counts are specific to the compiler that produced them - gcc and clang differ
# by up to 50% on these loops - so make perf refuses to compare across a change
# of toolchain. The line below is what it checks.
#
# toolchain: gcc (Ubuntu 13.3.0-6ubuntu2~24.04.1) 13.3.0
# valgrind:  valgrind-3.22.0

#
